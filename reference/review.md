# 敵対的な検査（機械の検査と、専門家役のレビュー）

見た目の検査（`export.mjs --check`）が通ったあと、中身を疑う検査を2つ行う。

| 検査 | やること | 出すもの |
|---|---|---|
| 機械の検査 | `audit.mjs` がページをまたいで数字・リンク・出典を突き合わせる | `review/<name>-audit.md` |
| 専門家役のレビュー | エージェントが専門家の役で厳しい質問を出し、資料だけを根拠に答えて A/B/C を付ける | `review/<name>-review.md` |

## 1. 機械の検査：audit.mjs

```bash
node <skill>/scripts/audit.mjs slides.html                # review/ に audit.md・text.md・pages.json
node <skill>/scripts/audit.mjs slides.html --online       # 外部リンクも開いて確かめる
node <skill>/scripts/audit.mjs slides.html --terms 売上高,営業利益   # 食い違いを見る言葉を足す
```

描いたあと（数字・グラフ・出典の番号・用語の下線が入ったあと）の各ページを読み、次を一覧にする。

| 種類 | 何を見るか | 扱い |
|---|---|---|
| 切れたリンク | `href="#id"` の飛び先がない | エラー（終了コード 1） |
| 出典の番号の不整合 | `/*CITES*/` のページ・行のページがデッキにない | エラー |
| 数字の食い違いの候補 | 同じ言葉（用語集の言葉・KPI の名前・`--terms`）のすぐ後ろの「数＋単位」が、ページで違う。「3年目」「7か月目」が付けば別の値として比べる。「5%以下」「6%超」のような線は、同じ向きの線どうしだけ比べる | 要確認（表示の桁で丸めて同じなら「丸めの違い」） |
| 出典のない数字 | 手で書いた「数＋単位」（`data-f` の外）があるのに、出典の番号も前提の一覧・付録へのリンクもないページ | 要確認 |
| 見出しが題名だけ | h1 が短く、主張が読み取れない（「市場規模」など） | 要確認 |
| 検査の赤枠 | `?check` の問題が残っている | 要確認 |
| 使われない用語・付録 | 本文に出ない用語、どこからもリンクされない付録 | 参考 |

エラーは直す。要確認は読んで、意図どおりなら残してよい（残す理由をレビューの 2-2 か注記に書く）。

## 2. 専門家役のレビュー

既定は **20人 × 5問 ＝ 100問**。ユーザーが人数・問いの数を指定したらそれに従う（例「5人×3問で」）。

### 手順

1. `audit.mjs` を実行し、`review/<name>-text.md`（描いたあとの本文）を用意する。**回答の根拠はこの本文だけ**（HTML のコメント・計算のコード・会話で聞いたことは使わない）
2. 資料の分野に合わせて専門家を選ぶ。お金・法務・運用・顧客・競合・技術・組織・リスクに散らし、同じ観点を2人に持たせない

   | 資料 | 例 |
   |---|---|
   | 事業計画・投資 | ベンチャーキャピタリスト、CFO・財務モデルの監査、業界の経営者、規制・法務の弁護士、物流・運用の責任者、マーケティングの責任者、顧客の代表、競合の立場、税理士、リスク管理 |
   | マーケティング | ブランドの責任者、メディアの買い手、データ分析、営業の責任者、顧客調査、法務（広告の表示）、財務（広告の投資対効果） |
   | コンサルの提言 | 依頼主の役員、現場の管理職、財務、IT、人事・労務、反対の立場の役員、外部の監査 |

3. 専門家ごとに「観点」（何を疑うか）を1文で書き、その観点から **資料の弱い所を突く** 質問を出す。ほめる質問・資料に書いてあることを確かめるだけの質問は出さない。数字の出どころ・前提の置き方・ページ間の食い違い・書かれていない仕組み・止める線を狙う
4. 質問ごとに、発表者として **資料の記載だけで** 答える。資料にない事実・数字は足さない。答えがなければ「資料には書かれていない」と書く。資料の数字を引くときはページを添える
5. 評価を付ける：**A** 資料で十分に答えられる／**B** 部分的に答えられる（前提・仮置き・これから確かめる）／**C** 資料に答えがない、または弱点。理由を1文で
6. 参照ページはページの id で書く（`build-review.mjs` が `p.12 #growth` にする）
7. 全員が終わったら、何人もが突いた論点（2-1）と、原文で確かめた食い違い（2-2）をまとめる。2-2 は `audit.mjs` の食い違いの候補も原文で確かめて入れる。専門家の読み違いに気づいて直した点は 2-3 に書く
8. `review/<name>-review.json` に書き、`build-review.mjs` で Markdown にする

```bash
node <skill>/scripts/build-review.mjs review/slides-review.json --experts 20 --questions 5
```

**並列にできるなら**：サブエージェントを使える環境では、専門家を4〜5人ずつに分けて並列に書かせ、`experts` をつなぐ。どのサブエージェントにも同じ `text.md`・同じ規則（資料だけで答える・A/B/C の意味）を渡し、観点が重ならないよう担当の分野を指定する。

### review.json の形

```json
{
  "title": "SENCHA BOX（見本）",
  "deck": "slides.html",
  "date": "2026-09-28",
  "summary": "（集計の後ろに1〜2文。C が多い理由など）",
  "experts": [
    {"role": "ベンチャーキャピタリスト", "view": "3年で21億円の根拠が、需要の証拠ではなく置いた値から来ていないかを突く",
     "qs": [
       {"title": "やめる割合4%の根拠は何か",
        "q": "質問の本文（2〜4文。どのページのどの数字を、なぜ疑うか）",
        "a": "回答（資料だけを根拠に。ページを添える）",
        "refs": ["kpi", "assump"], "grade": "C", "why": "4%は仮置きで、外部の調査より低い理由が書かれていない"}
     ]}
  ],
  "issues": [{"topic": "やめる割合の根拠", "by": [1, 2, 5], "deck": "前提の一覧に仮置きとあるだけ", "refs": ["kpi", "assump"]}],
  "conflicts": [{"refs": ["kpi", "ch03"], "what": "kpi は売上高20.9億円、中扉は21億円", "fixed": "中扉も20.9億円にした"}],
  "notes": ["Q03-2：専門家は◯◯を△△と読んでいたので、原文に合わせて直した"]
}
```

`build-review.mjs` は評価の集計（専門家ごとの A/B/C）・質問の一覧・専門家ごとの質疑応答・ページ別の参照索引（参照の多い上位10ページ・一度も参照されないページ）を作る。参照の id がデッキにない・評価が A/B/C でない・人数や問いの数が指定と違うと「注意」で知らせる。

### 出たあと

- 2-2 の食い違いは原文で確かめてから直し、`conflicts` の `fixed` に直した中身を書く（2-2 に「レビューのあと」の列が出る）。質問と回答は直す前の本文のまま残し、`method` にそう書く
- C が集まるページ・論点から直す（前提の一覧に根拠を足す、書かれていない仕組みを1枚足す、食い違いをそろえる）
- 直したら `audit.mjs` → レビューのやり直し（全員でなく、C を付けた専門家だけでもよい）。1回目で見つかった食い違いを直したあとの2回目は、別の食い違いを見つけやすい（見本では1回目で8件、直したあとの2回目で別の6件）
- 数字の食い違いは `audit.mjs` が拾えても、「新茶を毎月届ける」と「新茶は春だけ」のような言葉どうしの矛盾は拾えない。そこを専門家役のレビューで見る
- レビューの Markdown は資料の付録にしない（社内の確認用）
